# Агенты

Форк `akimovdigital/doop`. Сборка Doop Dev — ветка `local/doop-dev`. Схема форка: `docs/fork-workflow.md`. Журнал уроков: `docs/lessons.md`.

## Как работаем с Git

1. Работа по Doop Dev идёт в существующей основной рабочей области Orca на ветке `local/doop-dev`.
   - Несколько агентов могут работать в этой копии с распределением файлов и ответственности. При общей нагрузке проверки и тесты запускаются последовательно.
   - Новые ветки, рабочие копии и дополнительные сборки создаются только по отдельному поручению Никиты.
   - Перед задачей прочитать `docs/lessons.md`.
2. Коммит после каждого законченного логического шага. Коммиты маленькие, conventional commits. Секреты и ключи в коммиты не попадают.
3. Изменения Doop Dev фиксируются локально. Push выполняется по отдельному поручению. В `main`, `local/doop-dev` и чужие ветки напрямую не пушить. Force push запрещён, кроме своей отдельно порученной рабочей ветки до открытия PR.
4. Перед сдачей проверить diff, typecheck, lint, vitest и затронутый сценарий. Если vitest уже красный, нельзя добавлять новые падения. Для полной приёмки UI нужен скриншот.
   - Если отдельно порученная работа идёт через PR в форке, агент сам ревьюит diff и сливает squash-ом после проверок. Сборка Doop Dev.app выполняется на Маке по отдельному поручению.
5. Синхронизация с автором выполняется как отдельная задача. При порученном синке `main` форка перематывается до `upstream/main` только fast-forward. Правки автора интегрируются с сохранением правок Doop Dev и проходят проверки.
6. Кандидат в PR автору (`kgoedecke/doop`) готовится по отдельному поручению от свежего `upstream/main` в `upstream/…`, без брендинга Doop Dev, своего канала обновлений и `127.0.0.1:4437`. Открыть PR, писать комментарии, подписывать CLA у автора и публиковать сборки можно только после «да» Никиты.
7. Отчёт после каждого запуска, по-русски и коротко: что сделано, ветка и PR, SHA, проверки, что осталось.
8. Журнал `docs/lessons.md`.
   - После слитого PR, отклонённого или закрытого PR, синка с upstream и каждой пересборки дописать запись в том же PR или следующим коммитом. Отдельный PR только ради журнала не открывать.
   - Запись: дата, PR или синк со ссылкой, что сделали, что сработало, что сломалось и причина, урок или правило на будущее. Причину не выдумывать.
   - Повторяющийся урок перенести правилом в `.cursor/rules/git-workflow.mdc`.
